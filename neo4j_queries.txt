 SECTION 1 — GRAPH OVERVIEW
────────────────────────────────────────────────────────────────────────────────

[1.1] Count every node by label
  Shows how many nodes of each type exist in the whole graph.

  MATCH (n)
  RETURN labels(n)[0] AS label, count(n) AS total
  ORDER BY total DESC;

────────────────────────────────────────────────────────────────────────────────

[1.2] Count every relationship by type
  Shows how many edges of each kind exist (ADDED, MODIFIED, AST_CHILD, etc.).

  MATCH ()-[r]->()
  RETURN type(r) AS relationship, count(r) AS total
  ORDER BY total DESC;

────────────────────────────────────────────────────────────────────────────────

[1.3] Quick whole-graph sample (good starting visual)
  Returns a mixed subgraph — useful for a first look in Neo4j Browser.

  MATCH (n)-[r]->(m)
  RETURN n, r, m
  LIMIT 80;

 SECTION 2 — COMMITS & DEVELOPERS
────────────────────────────────────────────────────────────────────────────────

[2.1] Most active developers (by commit count)
  Ranks developers by how many commits they authored.

  MATCH (d:Developer)<-[:AUTHORED_BY]-(c:Commit)
  RETURN d.id AS developer, count(c) AS commits
  ORDER BY commits DESC
  LIMIT 20;

────────────────────────────────────────────────────────────────────────────────

[2.2] Commits that fix issues (with the issue they fix)
  Shows which commits are linked to issue references.

  MATCH (c:Commit)-[:FIXES_ISSUE]->(i:Issue)
  RETURN c.id AS commit, c.message AS message, i.id AS issue
  LIMIT 25;

────────────────────────────────────────────────────────────────────────────────

[2.3] Full commit context: developer → commit → files changed
  Shows who made a commit and which files it touched.

  MATCH (d:Developer)<-[:AUTHORED_BY]-(c:Commit)-[rel]->(f:File)
  WHERE type(rel) IN ['ADDED','MODIFIED','DELETED','RENAMED_TO']
  RETURN d.id AS developer, c.id AS commit,
         type(rel) AS change_type, f.id AS file
  LIMIT 40;

────────────────────────────────────────────────────────────────────────────────

[2.4] Developer → commit → issue (who fixed what)
  Traces a developer through their commits to the issues those commits fixed.

  MATCH (d:Developer)<-[:AUTHORED_BY]-(c:Commit)-[:FIXES_ISSUE]->(i:Issue)
  RETURN d.id AS developer, count(DISTINCT i) AS issues_fixed
  ORDER BY issues_fixed DESC
  LIMIT 15;

[4.6] Deepest AST nodes (highest depth value) across all files
  Finds the leaf nodes that are furthest from the root — reveals complex nesting.

  MATCH (a:ASTNode)

  RETURN a.file AS file, a.ast_type AS type, a.depth AS depth, a.value AS value
  ORDER BY depth DESC

[4.7] Average AST depth per file
  Ranks files by average depth of their AST — proxy for code complexity.

  MATCH (a:ASTNode)
  RETURN a.file AS file, avg(a.depth) AS avg_depth, max(a.depth) AS max_depth
  ORDER BY avg_depth DESC;

 SECTION 5 — CROSS-ENTITY (FILE + AST + COMMITS)
────────────────────────────────────────────────────────────────────────────────

[5.1] Commits that added a file which has an AST + who authored it
  Links commit history to the AST-bearing files (the base-snapshot files).

  MATCH (d:Developer)<-[:AUTHORED_BY]-(c:Commit)-[:ADDED]->(f:File)-[:HAS_AST]->(r:ASTNode)
  RETURN d.id AS developer, c.id AS commit, f.id AS file
  ORDER BY file
  LIMIT 30;

────────────────────────────────────────────────────────────────────────────────

[5.2] Visualise a Commit → File → AST root path  ← good graph visual
  Shows the chain: commit node → file node → AST root node.

  MATCH p = (c:Commit)-[:ADDED]->(f:File)-[:HAS_AST]->(r:ASTNode)
  RETURN p
  LIMIT 20;

────────────────────────────────────────────────────────────────────────────────

[5.3] Files modified most AND that have an AST (complexity hot spots)
  Cross-references churn (times modified) with AST size — the most changed
  AND most complex files are the riskiest.

  MATCH (c:Commit)-[:MODIFIED]->(f:File)-[:HAS_AST]->(r:ASTNode)
  WITH f, count(DISTINCT c) AS churn
  MATCH (a:ASTNode {file: f.id})
  RETURN f.id AS file, churn, count(a) AS ast_nodes
  ORDER BY churn DESC
  LIMIT 20;

────────────────────────────────────────────────────────────────────────────────

[5.4] Developer contribution to complex files (AST size as complexity proxy)
  Shows which developers worked on the largest AST files.

  MATCH (d:Developer)<-[:AUTHORED_BY]-(c:Commit)-[:MODIFIED]->(f:File)
  MATCH (a:ASTNode {file: f.id})
  WITH d, f, count(DISTINCT c) AS commits_on_file, count(a) AS ast_size
  RETURN d.id AS developer, f.id AS file, commits_on_file, ast_size
  ORDER BY ast_size DESC
  LIMIT 25;

 SECTION 7 — WHOLE-GRAPH VISUALIZATIONS  (paste in Neo4j Browser → graph view)

[7.1] The entire schema in one picture
  Shows one representative node of every label connected by one edge of every
  relationship type — a "map" of the graph schema without flooding the screen.

  MATCH (n)-[r]->(m)
  WITH labels(n)[0] AS fl, type(r) AS rel, labels(m)[0] AS tl, n, r, m,
       rand() AS rnd
  ORDER BY fl, rel, tl, rnd
  WITH fl, rel, tl, collect([n,r,m])[0] AS trio
  RETURN trio[0] AS n, trio[1] AS r, trio[2] AS m;

[7.11] Most-churned base file + its AST (complexity meets churn)

  The Project node is the single root everything belongs to.
  Two hops out gives a high-level overview of the entire knowledge graph.

 SECTION 8 — BASE VERSION GRAPH  (BASE_COMMIT = 408b29851d7bbe4d343340832297e4be7e0c5578)
 These queries focus exclusively on the snapshot of apache/groovy at commit #30
 (the first Java commit), which is the only version with AST subgraphs attached.
 Entities in this snapshot: 1 Project, 1 Branch, 1 Commit, 1 Developer,
 120 Files, 120 AST roots, 44,701 ASTNodes, 44,581 AST_CHILD edges.
────────────────────────────────────────────────────────────────────────────────

[8.1] ★ MASTER VISUALIZATION — every structural node of the base version
  Shows the complete skeleton: Project → Branch → Commit → Developer,
  Commit → all 120 File nodes, each File → its AST root node.
  AST internals (AST_CHILD edges) are excluded to keep the graph readable.
  This is the recommended starting point for the whole-base-version view.

  MATCH (c:Commit {id: '408b29851d7bbe4d343340832297e4be7e0c5578'})
  MATCH p1 = (proj:Project)<-[:BELONGS_TO]-(c)
  MATCH p2 = (branch:Branch)<-[:INSIDE_BRANCH]-(c)
  MATCH p3 = (c)-[:AUTHORED_BY]->(d:Developer)
  MATCH p4 = (c)-[:ADDED]->(f:File)
  MATCH p5 = (f)-[:HAS_AST]->(r:ASTNode)
  RETURN p1, p2, p3, p4, p5;

────────────────────────────────────────────────────────────────────────────────

[8.2] Base commit + files only (no AST) — fastest overview
  Just the commit node connected to all 120 files it added.
  Use this to find a specific file before drilling into its AST.

  MATCH p = (c:Commit {id: '408b29851d7bbe4d343340832297e4be7e0c5578'})-[:ADDED]->(f:File)
  RETURN p;

────────────────────────────────────────────────────────────────────────────────

[8.3] Base version: files grouped by package (colour by path prefix)
  Returns each file's path split into package prefix + filename so you can
  see which packages existed at the base snapshot. Table view is clearest.

  MATCH (c:Commit {id: '408b29851d7bbe4d343340832297e4be7e0c5578'})-[:ADDED]->(f:File)
  WITH f,
       split(f.id, '/') AS parts
  RETURN f.id AS file,
         reduce(pkg='', i IN range(0, size(parts)-2) | pkg + '/' + parts[i]) AS package,
         parts[-1] AS filename
  ORDER BY package, filename;

────────────────────────────────────────────────────────────────────────────────

[8.4] AST roots + 1 level of children for every base file
  One hop into the AST from each root — shows the top-level declarations
  (classes, imports, package) directly under each file's root node.

  MATCH p = (f:File)-[:HAS_AST]->(root:ASTNode)-[:AST_CHILD]->(child:ASTNode)
  RETURN p
  LIMIT 200;

────────────────────────────────────────────────────────────────────────────────

[8.5] Full AST for all small files (≤ 50 nodes) — safe to visualize completely
  Automatically selects only the files whose ASTs are small enough to render
  without overwhelming the browser. Typically 10-15 files.

  MATCH (a:ASTNode)
  WITH a.file AS file, count(a) AS n
  WHERE n <= 50
  MATCH p = (f:File {id: file})-[:HAS_AST]->(root:ASTNode)-[:AST_CHILD*]->(child:ASTNode)
  RETURN p;

────────────────────────────────────────────────────────────────────────────────

[8.6] Full AST for a single file — pick any file by name
  Replace the file id with any file from the base snapshot.
  Safe for files up to ~300 nodes; use [8.7] for larger ones.

  MATCH p = (f:File)-[:HAS_AST]->(root:ASTNode)-[:AST_CHILD*]->(child:ASTNode)
  WHERE f.id = 'src/main/org/codehaus/groovy/ast/MethodNode.java'
  RETURN p;

────────────────────────────────────────────────────────────────────────────────

[8.7] Controlled AST depth for large files (adjust depth as needed)
  For files with 300+ nodes, limit traversal depth to keep the graph clean.
  depth=2 shows class/method level; depth=3 adds statement level; depth=4+ gets crowded.

  MATCH p = (f:File)-[:HAS_AST]->(root:ASTNode)-[:AST_CHILD*..3]->(child:ASTNode)

────────────────────────────────────────────────────────────────────────────────

[8.8] AST leaf nodes only for a file (the terminal values)
  Shows only the leaf nodes — identifiers, literals, type names — without
  the internal tree structure. Good for seeing what names appear in a file.

  MATCH (f:File)-[:HAS_AST]->(root:ASTNode)-[:AST_CHILD*]->(leaf:ASTNode)
  WHERE f.id = 'src/main/org/codehaus/groovy/ast/MethodNode.java'
    AND leaf.is_leaf = true
  RETURN leaf.ast_type AS type, leaf.value AS value, leaf.depth AS depth
  ORDER BY depth, type;

────────────────────────────────────────────────────────────────────────────────

[8.9] AST declaration nodes across all base files (class/method/field structure)
  Shows every declaration-group node across the entire base snapshot.
  This is the "skeleton" of the codebase — all classes, methods, fields.

  MATCH (f:File)-[:HAS_AST]->(root:ASTNode)-[:AST_CHILD*]->(d:ASTNode)
  WHERE d.group = 'declaration'
  RETURN f.id AS file, d.ast_type AS declaration_type,
         d.depth AS depth, count(d) AS count
  ORDER BY file, depth;

[8.10] Base version: side-by-side AST comparison between two files
  Shows the ASTs of two files at depth 3 in the same graph view so you can

  MATCH p1 = (f1:File)-[:HAS_AST]->(r1:ASTNode)-[:AST_CHILD*..3]->(c1:ASTNode)

  RETURN p1, p2;

 SECTION 9 — AST DIFF / CHANGE MODELING  (ast_diff_experiment.py output)
================================================================================

Schema:  (:Commit)-[:HAS_AST_DIFF]->(:ASTDiff)-[:EDIT]->(:ASTEdit)
         (:File)-[:DIFFED_AT]->(:ASTDiff)
ASTDiff  {id, commit_id, file, n_insert, n_delete, n_update, n_move, total}
ASTEdit  {id, diff_id, action, node_type, node_label, new_label, parent_type, position}

[9.1] Count ASTDiff and ASTEdit nodes

  MATCH (d:ASTDiff) RETURN count(d) AS diffs;
  MATCH (e:ASTEdit) RETURN count(e) AS edits;

[9.2] Summary table: edits per commit-file pair (sorted by total)

  MATCH (d:ASTDiff)
  RETURN d.commit_id AS commit, d.file AS file,
         d.n_insert AS ins, d.n_delete AS del,
         d.n_update AS upd, d.n_move AS mov, d.total AS total
  ORDER BY d.total DESC;

[9.3] Which AST node types are most commonly inserted?

  MATCH (e:ASTEdit {action: 'insert'})
  RETURN e.node_type AS type, count(*) AS n
  ORDER BY n DESC LIMIT 20;

[9.4] Which AST node types are most commonly deleted?

  MATCH (e:ASTEdit {action: 'delete'})
  RETURN e.node_type AS type, count(*) AS n
  ORDER BY n DESC LIMIT 20;

[9.5] Which node types are updated (with old and new labels)?

  MATCH (e:ASTEdit {action: 'update'})
  RETURN e.node_type AS type, e.node_label AS old_label, e.new_label AS new_label
  LIMIT 30;

[9.6] Show all edits for one specific commit-file diff

  MATCH (d:ASTDiff {id: '3fa835bc::src/main/org/codehaus/groovy/ant/Groovyc.java'})
        -[:EDIT]->(e:ASTEdit)
  RETURN e.action, e.node_type, e.node_label, e.parent_type, e.position
  ORDER BY e.position;

[9.7] Full path: Commit -> ASTDiff -> ASTEdit (first 3 ASTEdits per diff)

  MATCH p = (c:Commit)-[:HAS_AST_DIFF]->(d:ASTDiff)-[:EDIT]->(e:ASTEdit)
  WITH c, d, collect(p)[..3] AS paths
  UNWIND paths AS p
  RETURN p;

[9.8] File evolution: all diffs on the same file across commits

  MATCH (f:File {id: 'src/main/org/codehaus/groovy/ant/Groovyc.java'})
        -[:DIFFED_AT]->(d:ASTDiff)
  RETURN d.commit_id AS commit, d.n_insert AS ins, d.n_delete AS del,
         d.n_update AS upd, d.n_move AS mov, d.total AS total
  ORDER BY d.commit_id;

[9.9] What parent node types surround the most inserts?

  MATCH (e:ASTEdit {action: 'insert'})
  WHERE e.parent_type <> ''
  RETURN e.parent_type AS parent, count(*) AS n
  ORDER BY n DESC LIMIT 15;

[9.10] Connect commit author to the type of AST edits they make

  MATCH (c:Commit)-[:AUTHORED_BY]->(dev:Developer)
  MATCH (c)-[:HAS_AST_DIFF]->(d:ASTDiff)-[:EDIT]->(e:ASTEdit)
  RETURN dev.email AS author, e.action AS action, count(*) AS n
  ORDER BY n DESC LIMIT 20;

[9.11] Visualise one commit's full diff graph (commit + diff + edits)

  MATCH p1 = (c:Commit)-[:HAS_AST_DIFF]->(d:ASTDiff)
  MATCH p2 = (d)-[:EDIT]->(e:ASTEdit)
  WHERE d.file = 'src/main/org/codehaus/groovy/ant/Groovyc.java'
  RETURN p1, p2 LIMIT 100;

 SECTION 10 — DELTA GRAPH  (build_delta_graph.py output)  ★ current approach
================================================================================

This is the change-modeling approach used for bug detection: each Commit links
DIRECTLY to the ASTNodes it changed (no intermediate diff/edit nodes like
Section 9). Four edge types go from a Commit to an ASTNode:

  (Commit)-[:REMOVES]->(ASTNode)                          node deleted by commit
  (Commit)-[:ADDS]->(ASTNode {is_delta:true})            new node inserted
  (Commit)-[:UPDATES {old_value,new_value}]->(ASTNode)   node value changed
  (Commit)-[:MOVES {new_parent_type,new_pos}]->(ASTNode) node relocated

Inserted nodes (is_delta=true) are also wired into the AST via a new
AST_CHILD edge to their parent, so an added subtree sits in real code context.
Coverage: 120 base files, 34 commits carry deltas. Built only for the first
commit that touched each base file (parent state == BASE_COMMIT), so positions
line up with the base-snapshot ASTNodes.

----------------------------------------------------------------------------
 10A — OVERVIEW & SANITY CHECKS
----------------------------------------------------------------------------

[10.1] Count each delta edge type (whole graph)
  How many adds / removes / updates / moves exist in total.

  MATCH ()-[r:ADDS|REMOVES|UPDATES|MOVES]->()
  RETURN type(r) AS change, count(r) AS total
  ORDER BY total DESC;

[10.2] How many commits carry delta edges, and how many files are affected
  Quick coverage check of the delta layer.

  MATCH (c:Commit)-[r:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  RETURN count(DISTINCT c) AS commits_with_deltas,
         count(DISTINCT a.file) AS files_touched,
         count(r) AS total_delta_edges;

[10.3] Inserted (delta) ASTNodes count
  Nodes created by commits (flagged is_delta) vs. original base nodes.

  MATCH (a:ASTNode {is_delta: true})
  RETURN count(a) AS inserted_nodes;

----------------------------------------------------------------------------
 10B — ONLINE COMMIT ARRIVAL  (inspect commits one by one, as they "arrive")
----------------------------------------------------------------------------

[10.4] Per-commit change summary (the delta "feed", busiest first)
  One row per commit: how many of each change type it introduced. This is the
  table to watch when inspecting the stream of commits and their AST impact.

  MATCH (c:Commit)-[r:ADDS|REMOVES|UPDATES|MOVES]->(:ASTNode)
  RETURN c.id AS commit,
         sum(CASE type(r) WHEN 'ADDS'    THEN 1 ELSE 0 END) AS adds,
         sum(CASE type(r) WHEN 'REMOVES' THEN 1 ELSE 0 END) AS removes,
         sum(CASE type(r) WHEN 'UPDATES' THEN 1 ELSE 0 END) AS updates,
         sum(CASE type(r) WHEN 'MOVES'   THEN 1 ELSE 0 END) AS moves,
         count(r) AS total
  ORDER BY total DESC;

[10.5] Per-commit summary WITH author and message (full arrival context)
  Same feed as 10.4 but joined to who made the commit and its message —
  reads like a change log of AST-level modifications.

  MATCH (c:Commit)-[r:ADDS|REMOVES|UPDATES|MOVES]->(:ASTNode)
  OPTIONAL MATCH (c)-[:AUTHORED_BY]->(d:Developer)
  RETURN c.id AS commit, d.id AS author,
         substring(c.message, 0, 60) AS message,
         count(r) AS delta_edges
  ORDER BY delta_edges DESC;

[10.6] Per-commit, per-file breakdown (which file did each commit change, how)
  Expands a commit into the individual files it modified and the counts per
  file — use to drill from a commit down to its affected files.

  MATCH (c:Commit)-[r:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  RETURN c.id AS commit, a.file AS file,
         type(r) AS change, count(r) AS n
  ORDER BY commit, file, change;

[10.7] Inspect ONE commit's modifications in full (table)
  Every AST node a single commit changed, with the change type and the node's
  identity / position. Replace the commit id with any from 10.4.

  MATCH (c:Commit {id: 'ec6321cde182487f05c420be436833f232e78862'})
        -[r:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  RETURN type(r) AS change, a.file AS file, a.ast_type AS node_type,
         a.value AS value, a.pos_line AS line,
         r.old_value AS old_value, r.new_value AS new_value,
         r.new_parent_type AS moved_under
  ORDER BY file, line;

----------------------------------------------------------------------------
 10C — INSPECT MODIFICATIONS IN CONTEXT OF THE MAIN KG (AST + files)
----------------------------------------------------------------------------

[10.8] Updated nodes with their old vs. new values (the clearest "what changed")
  Shows every UPDATES edge — the exact value before and after the commit.

  MATCH (c:Commit)-[r:UPDATES]->(a:ASTNode)
  RETURN c.id AS commit, a.file AS file, a.ast_type AS node_type,
         r.old_value AS old_value, r.new_value AS new_value, a.pos_line AS line
  ORDER BY file, line;

[10.9] What node types get added / removed most often
  Aggregates the kinds of AST nodes that commits insert and delete — reveals
  the typical shape of changes (e.g. many MethodInvocation inserts).

  MATCH (c:Commit)-[r:ADDS|REMOVES]->(a:ASTNode)
  RETURN type(r) AS change, a.ast_type AS node_type, count(*) AS n
  ORDER BY change, n DESC
  LIMIT 40;

[10.10] A removed node together with the base code around it
  For each REMOVES, show the deleted node plus its parent in the original AST,
  so you see what structure was taken out and from where.

  MATCH (c:Commit)-[:REMOVES]->(a:ASTNode)
  OPTIONAL MATCH (parent:ASTNode)-[:AST_CHILD]->(a)
  RETURN c.id AS commit, a.file AS file,
         parent.ast_type AS parent_type, a.ast_type AS removed_type,
         a.value AS removed_value, a.pos_line AS line
  ORDER BY file, line
  LIMIT 50;

[10.11] Delta evolution of one file across commits
  Every commit that changed a given file, with the per-type counts. Change the
  file id to follow any base file's modification history at the AST level.

  MATCH (c:Commit)-[r:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  WHERE a.file = 'src/main/org/codehaus/groovy/ast/ASTNode.java'
  RETURN c.id AS commit, type(r) AS change, count(r) AS n
  ORDER BY commit, change;

[10.12] Files ranked by how much they were modified at the AST level
  Sums all delta edges per file — the AST-level churn hotspots (compare with
  [3.1] which counts whole-file commits).

  MATCH (c:Commit)-[r:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  RETURN a.file AS file, count(r) AS delta_edges,
         count(DISTINCT c) AS commits
  ORDER BY delta_edges DESC
  LIMIT 25;

================================================================================
 SECTION 11 — ONLINE KG GROWTH & BUG LABELS  (apply_commit_labels.py +
              build_online_kg.py)   ★ the online procedure
================================================================================

The KG is scoped to the 8,059 ApacheJIT-labelled commits (apache_groovy.csv).
Each Commit node carries:
  buggy     : bool   - JIT defect label (introduced a later-fixed bug)
  is_fix    : bool   - this commit is itself a bug-fix
  in_jit    : bool   - belongs to the labelled study set
  author_ts : int    - author UNIX timestamp = the ONLINE ARRIVAL ORDER
  la,ld,nf,nd,ns,ent,ndev,age,nuc,aexp,arexp,asexp : JIT change metrics

Online growth model: process commits in author_ts order; each commit gets its
delta graph (Section 10 edges) against the evolving AST; ADDED files get a full
AST subgraph (HAS_AST) like the base snapshot; DELETED files have their nodes
REMOVES-marked. At inference time for a commit, every EARLIER commit's label is
known — queries 11.5–11.7 reproduce that online evaluation view.

----------------------------------------------------------------------------
 11A — LABEL DISTRIBUTION  (works now)
----------------------------------------------------------------------------

[11.1] Overall label balance
  The buggy/benign split of the whole labelled set.

  MATCH (c:Commit {in_jit: true})
  RETURN c.buggy AS buggy, count(c) AS commits
  ORDER BY buggy;

[11.2] Bug rate per year (class balance drift over time)
  How the proportion of buggy commits changes year by year — important for an
  online/temporal train-test split.

  MATCH (c:Commit {in_jit: true})
  RETURN c.jit_year AS year, count(c) AS commits,
         sum(CASE WHEN c.buggy THEN 1 ELSE 0 END) AS buggy,
         round(100.0 * sum(CASE WHEN c.buggy THEN 1 ELSE 0 END) / count(c), 1) AS buggy_pct
  ORDER BY year;

[11.3] Buggy-commit change-metric profile vs benign
  Compares the average JIT metrics of buggy vs benign commits — a quick sanity
  check that buggy commits are larger / more scattered.

  MATCH (c:Commit {in_jit: true})
  RETURN c.buggy AS buggy, count(c) AS n,
         round(avg(c.la), 1) AS avg_lines_added,
         round(avg(c.ld), 1) AS avg_lines_deleted,
         round(avg(c.nf), 2) AS avg_files,
         round(avg(c.ent), 3) AS avg_entropy
  ORDER BY buggy;

[11.4] Bug-fixing commits and the issues they close
  The is_fix commits joined to their FIXES_ISSUE targets — the fix side of the
  buggy/fix relationship.

  MATCH (c:Commit {in_jit: true, is_fix: true})
  OPTIONAL MATCH (c)-[:FIXES_ISSUE]->(i:Issue)
  RETURN c.id AS commit, substring(c.message,0,50) AS message,
         collect(i.id) AS issues
  ORDER BY c.author_ts
  LIMIT 30;

----------------------------------------------------------------------------
 11B — ONLINE ARRIVAL ORDER  (the commit stream as it "arrives")
----------------------------------------------------------------------------

[11.5] The commit stream in arrival order (oldest first)
  Walks the labelled commits chronologically — this is the order the online
  procedure ingests them. Add SKIP/LIMIT to page through the stream.

  MATCH (c:Commit {in_jit: true})
  RETURN c.author_ts AS ts, c.jit_year AS year, c.id AS commit,
         c.buggy AS buggy, c.is_fix AS is_fix
  ORDER BY c.author_ts
  LIMIT 50;

[11.6] Online snapshot: state of the world WHEN one commit arrives
  For a chosen "current" commit, everything already known (all earlier labelled
  commits + their labels). This is the training window available to predict the
  current commit. Replace the id with the commit under evaluation.

  MATCH (cur:Commit {id: 'a322a829a586...' })          // <- commit being predicted
  MATCH (past:Commit {in_jit: true})
  WHERE past.author_ts < cur.author_ts
  RETURN count(past) AS known_history,
         sum(CASE WHEN past.buggy THEN 1 ELSE 0 END) AS known_buggy,
         round(100.0*sum(CASE WHEN past.buggy THEN 1 ELSE 0 END)/count(past),1) AS prior_bug_rate;

[11.7] Sliding online window: label balance up to each year
  Cumulative buggy/benign counts as of the end of each year — shows how the
  prior bug-rate (a baseline predictor) evolves through the online stream.
  (Uses reduce() for the running total — portable across Neo4j versions.)

  MATCH (c:Commit {in_jit: true})
  WITH c.jit_year AS year, count(c) AS yt,
       sum(CASE WHEN c.buggy THEN 1 ELSE 0 END) AS yb
  ORDER BY year
  WITH collect({year: year, yt: yt, yb: yb}) AS rows
  UNWIND range(0, size(rows)-1) AS i
  RETURN rows[i].year AS year, rows[i].yt AS yr_total, rows[i].yb AS yr_buggy,
         reduce(s=0, j IN range(0,i) | s + rows[j].yt) AS cumulative_commits,
         reduce(s=0, j IN range(0,i) | s + rows[j].yb) AS cumulative_buggy;

----------------------------------------------------------------------------
 11C — KG GROWTH PER COMMIT  (needs build_online_kg.py to have run)
----------------------------------------------------------------------------

[11.8] How the graph grew: files & AST added vs delta-only per commit
  Per commit: how many files it ADDED with a fresh AST (HAS_AST) vs how many it
  only modified via delta edges. Shows the "new subgraph vs delta" split.

  MATCH (c:Commit {in_jit: true})
  OPTIONAL MATCH (c)-[:ADDED]->(nf:File)-[:HAS_AST]->()
  OPTIONAL MATCH (c)-[dr:ADDS|REMOVES|UPDATES|MOVES]->(:ASTNode)
  RETURN c.id AS commit, c.author_ts AS ts,
         count(DISTINCT nf) AS new_file_asts,
         count(dr) AS delta_edges
  ORDER BY ts
  LIMIT 50;

[11.9] Cumulative AST node growth over the stream (space-efficiency check)
  Counts base + inserted (is_delta) ASTNodes — confirms the graph grows by
  deltas, not by re-storing whole ASTs per commit.

  MATCH (a:ASTNode)
  RETURN count(a) AS total_ast_nodes,
         sum(CASE WHEN a.is_delta THEN 1 ELSE 0 END) AS delta_nodes,
         sum(CASE WHEN a.is_delta IS NULL THEN 1 ELSE 0 END) AS base_nodes;

[11.10] Files that gained an AST after the base snapshot (new files over time)
  Files with HAS_AST whose creating commit is NOT the base commit — i.e. files
  born during the online stream.

  MATCH (c:Commit {in_jit: true})-[:ADDED]->(f:File)-[:HAS_AST]->(:ASTNode)
  RETURN c.author_ts AS ts, c.id AS commit, f.id AS new_file
  ORDER BY ts
  LIMIT 50;

----------------------------------------------------------------------------
 11D — LABEL × DELTA  (link bug labels to AST change shape; needs engine)
----------------------------------------------------------------------------

[11.11] Average AST-delta size: buggy vs benign commits
  Do buggy commits make structurally bigger AST changes? Joins the delta layer
  to the label — a candidate signal for the GNN / inference.

  MATCH (c:Commit {in_jit: true})
  OPTIONAL MATCH (c)-[r:ADDS|REMOVES|UPDATES|MOVES]->(:ASTNode)
  WITH c, count(r) AS delta_edges
  RETURN c.buggy AS buggy, count(c) AS commits,
         round(avg(delta_edges), 1) AS avg_delta_edges
  ORDER BY buggy;

[11.12] Which AST node types are most touched by BUGGY commits
  The node-type fingerprint of buggy changes (vs all changes) — useful for
  feature analysis.

  MATCH (c:Commit {in_jit: true, buggy: true})
        -[r:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  RETURN a.ast_type AS node_type, type(r) AS change, count(*) AS n
  ORDER BY n DESC
  LIMIT 30;

[11.13] One buggy commit, full picture: label + metrics + AST delta (visual)
  A single buggy commit with its changed AST nodes — inspect what a labelled
  defect-introducing change looks like structurally. Replace the id.

  MATCH (c:Commit {in_jit: true, buggy: true})
  WITH c LIMIT 1
  MATCH p = (c)-[r:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  RETURN p;

 13A — STATISTICAL OVERVIEW  (numbers / tables)

[13.1] One-line health snapshot of the whole graph
  Totals for the headline node/edge populations in a single row.

  MATCH (a:ASTNode) WITH count(a) AS ast
  MATCH (c:Commit) WITH ast, count(c) AS commits
  MATCH (f:File) WITH ast, commits, count(f) AS files
  RETURN ast AS astnodes, commits, files,
         count{ ()-[:ADDS]->() }    AS adds,
         count{ ()-[:REMOVES]->() } AS removes,
         count{ ()-[:UPDATES]->() } AS updates,
         count{ ()-[:MOVES]->() }   AS moves,
         count{ ()-[:AST_CHILD]->() } AS ast_child;

[13.2] ASTNode population breakdown (alive / removed / inserted / base)
  The composition of the AST layer after full evolution.

  MATCH (a:ASTNode)
  RETURN count(a) AS total,
         sum(CASE WHEN a.is_delta THEN 1 ELSE 0 END) AS inserted_by_commits,
         sum(CASE WHEN a.alive=false THEN 1 ELSE 0 END) AS removed,
         sum(CASE WHEN a.alive=true THEN 1 ELSE 0 END) AS alive,
         sum(CASE WHEN a.alive IS NULL THEN 1 ELSE 0 END) AS untouched_base,
         sum(CASE WHEN a.pos_line>0 THEN 1 ELSE 0 END) AS positioned;

[13.3] Delta-layer coverage of the labelled commit stream
  How many of the 8,059 in_jit commits actually changed the AST.

  MATCH (c:Commit {in_jit:true})
  OPTIONAL MATCH (c)-[r:ADDS|REMOVES|UPDATES|MOVES]->()
  WITH c, count(r) AS d
  RETURN count(c) AS in_jit_commits,
         sum(CASE WHEN d>0 THEN 1 ELSE 0 END) AS with_ast_delta,
         sum(CASE WHEN d=0 THEN 1 ELSE 0 END) AS no_ast_delta;

[13.4] File-type coverage: which files have an AST and which don't
  Splits File nodes into Java-with-AST, Java-without-AST (gaps), and non-Java
  (expected to have no AST).

  MATCH (f:File)
  WITH f, f.id ENDS WITH '.java' AS is_java, exists((f)-[:HAS_AST]->()) AS has_ast
  RETURN
    sum(CASE WHEN is_java AND has_ast THEN 1 ELSE 0 END) AS java_with_ast,
    sum(CASE WHEN is_java AND NOT has_ast THEN 1 ELSE 0 END) AS java_without_ast,
    sum(CASE WHEN NOT is_java THEN 1 ELSE 0 END) AS non_java;

[13.5] AST node-type distribution across the whole live graph
  The 30 most common javalang node types (over all ASTNodes).

  MATCH (a:ASTNode)
  RETURN a.ast_type AS ast_type, a.group AS group, count(*) AS n
  ORDER BY n DESC LIMIT 30;

[13.6] Delta volume per year (how much code change the stream models over time)

  MATCH (c:Commit {in_jit:true})-[r:ADDS|REMOVES|UPDATES|MOVES]->()
  RETURN c.jit_year AS year, count(DISTINCT c) AS commits, count(r) AS delta_edges
  ORDER BY year;

----------------------------------------------------------------------------
 13B — DATA-QUALITY / SANITY CHECKS  (find bugs & missings)
 Each of these SHOULD return ~0 (or a small, explainable number). Non-zero
 rows that you can't explain are candidate bugs to fix.
----------------------------------------------------------------------------

[13.7] MISSING ASTs: .java files modified by a labelled commit but never parsed
  These are the genuine gaps (parser failed on both JavaParser and JDT).
  Expected: a small handful (~5).

  MATCH (c:Commit {in_jit:true})-[:MODIFIED]->(f:File)
  WHERE f.id ENDS WITH '.java' AND NOT (f)-[:HAS_AST]->()
  RETURN DISTINCT f.id AS missing_ast_file
  ORDER BY missing_ast_file;

[13.8] Commits that changed nothing in the AST layer (no-delta in_jit commits)
  Either touched only non-Java files, made an import-only/whitespace change, or
  were parse-skipped. Inspect a few to confirm they are legitimately empty.

  MATCH (c:Commit {in_jit:true})
  WHERE NOT (c)-[:ADDS|REMOVES|UPDATES|MOVES]->()
  OPTIONAL MATCH (c)-[:MODIFIED|ADDED|DELETED]->(f:File)
  RETURN c.id AS commit, substring(c.message,0,50) AS message,
         collect(DISTINCT split(f.id,'.')[-1])[0..6] AS file_exts
  LIMIT 40;

[13.9] Schema integrity: a file must have exactly one AST root
  Should return NOTHING. >1 root means a duplicate-attach bug.

  MATCH (f:File) WITH f, count{ (f)-[:HAS_AST]->() } AS roots
  WHERE roots > 1
  RETURN f.id AS file, roots;

[13.10] Delta/flag consistency checks (each should be ~0)
  (a) removed nodes that lack a REMOVES edge; (b) nodes with a REMOVES edge
  still marked alive; (c) is_delta nodes without an ADDS edge.

  MATCH (a:ASTNode) WHERE a.alive=false AND NOT ()-[:REMOVES]->(a)
  RETURN 'removed_without_REMOVES_edge' AS check, count(a) AS n
  UNION
  MATCH (a:ASTNode) WHERE ()-[:REMOVES]->(a) AND coalesce(a.alive,true)
  RETURN 'REMOVES_edge_but_still_alive' AS check, count(a) AS n
  UNION
  MATCH (a:ASTNode {is_delta:true}) WHERE NOT ()-[:ADDS]->(a)
  RETURN 'is_delta_without_ADDS_edge' AS check, count(a) AS n;

[13.11] No-op UPDATES (old_value == new_value) — should be tiny

  MATCH ()-[u:UPDATES]->(a:ASTNode)
  WHERE u.old_value = u.new_value
  RETURN a.file AS file, a.ast_type AS type, u.old_value AS value
  LIMIT 25;

[13.12] Fully-deleted files that still keep a (dead) AST
  Files whose every AST node is alive=false — the file was removed; its AST is
  retained as history. Useful to know, not necessarily a bug.

  MATCH (f:File)-[:HAS_AST]->()
  WITH f, count{ (a:ASTNode {file:f.id}) WHERE coalesce(a.alive,true) } AS alive
  WHERE alive = 0
  RETURN f.id AS fully_deleted_file
  LIMIT 50;

[13.13] Commit-stream metadata completeness (should all be 0)
  Labelled commits missing the fields the online pipeline relies on.

  MATCH (c:Commit {in_jit:true})
  RETURN sum(CASE WHEN c.author_ts IS NULL THEN 1 ELSE 0 END) AS missing_author_ts,
         sum(CASE WHEN c.buggy IS NULL THEN 1 ELSE 0 END) AS missing_buggy,
         sum(CASE WHEN c.la IS NULL THEN 1 ELSE 0 END) AS missing_metrics;

[13.14] Orphan ASTNodes whose declared file has no File node  (SLOW — full scan)
  Should be 0. Run sparingly; it scans all ASTNodes.

  MATCH (a:ASTNode)
  WHERE NOT EXISTS { MATCH (f:File {id:a.file}) }
  RETURN count(a) AS orphan_astnodes;

----------------------------------------------------------------------------
 13C — EVOLVING-AST ANALYTICS  (churn / current live state)
----------------------------------------------------------------------------

[13.15] Most-evolved files (by total delta edges) — the AST-churn hotspots

  MATCH (c:Commit {in_jit:true})-[r:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  RETURN a.file AS file, count(r) AS delta_edges,
         count(DISTINCT c) AS commits_touching
  ORDER BY delta_edges DESC LIMIT 20;

[13.16] Current LIVE AST size per file vs removed (dead) nodes
  The size of each file's current tree (alive) and how much history (removed)
  sits behind it.

  MATCH (a:ASTNode)
  RETURN a.file AS file,
         sum(CASE WHEN coalesce(a.alive,true) THEN 1 ELSE 0 END) AS live_nodes,
         sum(CASE WHEN a.alive=false THEN 1 ELSE 0 END) AS removed_nodes
  ORDER BY live_nodes DESC LIMIT 20;

[13.17] Which AST node types are most ADDED vs REMOVED across all commits
  The structural fingerprint of change in the whole project.

  MATCH (c:Commit {in_jit:true})-[r:ADDS|REMOVES]->(a:ASTNode)
  RETURN a.ast_type AS node_type, type(r) AS change, count(*) AS n
  ORDER BY n DESC LIMIT 30;

----------------------------------------------------------------------------
 13D — LABEL x STRUCTURE  (the bug-detection signal, full KG)
----------------------------------------------------------------------------

[13.18] Average AST-delta size: buggy vs benign (full KG)
  Headline signal: buggy commits make structurally much bigger changes
  (~860 delta edges on average vs ~299 for benign).

  MATCH (c:Commit {in_jit:true})
  OPTIONAL MATCH (c)-[r:ADDS|REMOVES|UPDATES|MOVES]->()
  WITH c, count(r) AS d
  RETURN c.buggy AS buggy, count(c) AS commits,
         round(avg(d),1) AS avg_delta_edges,
         round(avg(c.la),1) AS avg_lines_added, round(avg(c.ent),3) AS avg_entropy
  ORDER BY buggy;

[13.19] Buggy-change node-type fingerprint vs benign (normalized share)
  For each node type, the share of buggy-commit changes vs benign — types whose
  share is higher under buggy commits are candidate risk signals.

  MATCH (c:Commit {in_jit:true})-[r:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  WITH c.buggy AS buggy, a.ast_type AS t, count(*) AS n
  RETURN t AS node_type,
         sum(CASE WHEN buggy THEN n ELSE 0 END) AS buggy_changes,
         sum(CASE WHEN NOT buggy THEN n ELSE 0 END) AS benign_changes
  ORDER BY buggy_changes DESC LIMIT 25;

[13.20] Per-year bug rate (temporal class balance for online splits)

  MATCH (c:Commit {in_jit:true})
  RETURN c.jit_year AS year, count(c) AS commits,
         sum(CASE WHEN c.buggy THEN 1 ELSE 0 END) AS buggy,
         round(100.0*sum(CASE WHEN c.buggy THEN 1 ELSE 0 END)/count(c),1) AS buggy_pct
  ORDER BY year;

 13E — FULL-KG VISUALIZATIONS  (Graph tab; summarized + sampled subgraphs)
----------------------------------------------------------------------------

[13.21] The schema meta-graph (one node per label, one edge per type)
  A compact "map" of the whole KG schema — the fastest way to see every node
  and relationship type at once.

  MATCH (n)-[r]->(m)
  WITH labels(n)[0] AS fl, type(r) AS rel, labels(m)[0] AS tl, n, r, m, rand() AS x
  ORDER BY fl, rel, tl, x
  WITH fl, rel, tl, collect([n,r,m])[0] AS t
  RETURN t[0] AS n, t[1] AS r, t[2] AS m;

[13.22] A heavily-evolved file: its current AST (depth 3) + every commit that
        changed it. Shows real long-term evolution on one structure.

  MATCH (f:File) WHERE f.id CONTAINS 'DefaultGroovyMethods.java'
  CALL (f) {
    MATCH p=(f)-[:HAS_AST]->(:ASTNode)-[:AST_CHILD*0..3]->(:ASTNode) RETURN p LIMIT 400
  }
  WITH f, collect(p) AS ast
  MATCH p2=(c:Commit)-[:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  WHERE a.file = f.id
  RETURN ast, collect(p2)[0..150] AS deltas;

[13.23] A brand-new file born in the stream: creating commit + its full AST
  Replace nothing — auto-picks one file added (with AST) after BASE.

  MATCH (c:Commit {in_jit:true})-[:ADDED]->(f:File)-[:HAS_AST]->(root:ASTNode)
  WHERE NOT (:Commit {id:'408b29851d7bbe4d343340832297e4be7e0c5578'})-[:ADDED]->(f)
  WITH c, f, root LIMIT 1
  MATCH p = (c)-[:ADDED]->(f)-[:HAS_AST]->(root)-[:AST_CHILD*0..4]->(:ASTNode)
  RETURN p LIMIT 300;

[13.24] A buggy commit's complete neighbourhood (process + code in one view)
  Author, fixed issue(s), files touched, and the AST nodes it changed —
  the full multi-modal context the model sees for one defect-introducing commit.

  MATCH (c:Commit {in_jit:true, buggy:true})-[:ADDS|REMOVES|UPDATES|MOVES]->()
  WITH c LIMIT 1
  OPTIONAL MATCH p1=(c)-[:AUTHORED_BY]->(:Developer)
  OPTIONAL MATCH p2=(c)-[:FIXES_ISSUE]->(:Issue)
  OPTIONAL MATCH p3=(c)-[:MODIFIED|ADDED|DELETED]->(:File)
  OPTIONAL MATCH p4=(c)-[:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  RETURN c, p1, p2, p3, collect(p4)[0..120] AS deltas;

[13.25] Developer subgraph: one author, their commits, and the files they hit
  A meta-path C-Dev and C-File view for the busiest developer-style queries.
  Replace the substring with any developer.

  MATCH (d:Developer) WHERE toLower(d.id) CONTAINS 'james'
  WITH d LIMIT 1
  MATCH p=(d)<-[:AUTHORED_BY]-(c:Commit {in_jit:true})-[:MODIFIED|ADDED]->(:File)
  RETURN p LIMIT 150;

[13.26] Issue -> fixing commit -> its AST delta (link a bug report to the code)
  Traces an issue to the commit that fixed it and the AST nodes that commit
  changed — the repair, in structural form.

  MATCH (i:Issue)<-[:FIXES_ISSUE]-(c:Commit {in_jit:true})-[:ADDS|REMOVES|UPDATES|MOVES]->()
  WITH i, c LIMIT 1
  MATCH p1=(i)<-[:FIXES_ISSUE]-(c)
  MATCH p2=(c)-[:ADDS|REMOVES|UPDATES|MOVES]->(a:ASTNode)
  RETURN p1, collect(p2)[0..120] AS deltas;
